# Inbox API contract and implementation status

The repository includes a tenant-scoped SQLite backend for canonical customers, Inbox snapshots, CRM, orders, manual shipment tracking, care tickets, and market research. Live mode is the default outside tests; `VITE_APP_MODE=demo` explicitly selects browser-local fixtures. Live API failures never fall back to Demo data. Social channel authorization, message ingestion/outbound delivery, uploads and Inbox AI are not connected. Market research uses Gemini with Google Search grounding and returns a concise analysis; see [AI market intelligence](AI_MARKET_INTELLIGENCE.md).

Requests use JSON and `credentials: include`, with a 15-second timeout. In development, the Vite proxy forwards `/api/v1` to the SQLite server. Production requires a same-origin HTTPS reverse proxy. The backend enforces tenant isolation, permissions, validation, audit logging and Origin checks for cookie-authenticated mutations. Never place provider secrets in Vite environment variables: `VITE_*` values are public browser configuration.

| Method | Path relative to base URL     | Request             | Success response            |
| ------ | ----------------------------- | ------------------- | --------------------------- |
| GET    | `/inbox`                      | —                   | `InboxData`                 |
| PATCH  | `/conversations/:id`          | `ConversationPatch` | Full updated `Conversation` |
| PATCH  | `/customers/:id`              | `CustomerPatch`     | Full updated `Customer`     |
| POST   | `/customers`                  | `CustomerInput`     | Full created `Customer`     |
| POST   | `/conversations/:id/messages` | `SendMessageInput`  | Full updated `Conversation` |

Canonical TypeScript shapes live in `src/types/inbox.ts`. Responses are direct objects, without a `data` wrapper. The frontend validates Inbox structure and entity references on load, and validates full mutation responses plus their matching requested IDs before updating the UI. Invalid JSON and malformed data show explicit errors. Return non-2xx status for failures. The frontend displays a status-based error; tenant-scoped database errors do not fall back to local fixtures. Future work includes server-side pagination/search, realtime subscriptions, optimistic concurrency, secure object storage uploads, and channel-specific outbound capability checks.

Conversation status values: `open`, `pending`, `resolved`, `closed`. All explicit status changes are supported. Sending an outbound reply to a resolved conversation reopens it; a closed conversation must first be reopened. Internal notes are allowed on closed conversations. Assignee and team IDs may be `null`. Tags have a maximum of 10 entries and 40 characters per entry.

Demo messages are local only. Their delivery state is `sent`, never a claim of provider delivery. Attachments accept up to 4 files, each at most 1 MB; browser storage capacity can impose a smaller aggregate limit. Supported types are PNG, JPEG, WebP, GIF, PDF, and plain text (TXT). Persisted file metadata may omit `url`, which must be shown as a metadata-only attachment rather than a successful upload. Selected files persist as data URLs; the seed image is a bundled SVG. Demo rejects arbitrary external attachment URLs and temporary blob URLs. A Live backend may return HTTP(S) attachment URLs and needs a dedicated authenticated upload flow for production files.

Customer creation assigns a stable ID and the Demo adapter rejects a duplicate email (case insensitive) or phone (punctuation ignored, Vietnamese +84 normalized to 0). Updates enforce the same checks. The backend must enforce uniqueness within its tenant transaction. Contacts are canonical across Inbox, CRM, orders and tickets; see the [operations contract](operations-api.md).

Marketplace/social connectors, account-level OAuth, message ingestion, privacy controls, model analysis and Demo behavior are defined in [Channel integration](channel-integration.md). The API currently returns an explicit unavailable/not-configured error for provider operations; it does not pretend that a channel is connected or a message was delivered.

Orders can include optional `conversationId` and `clientRequestId`. APIs should echo both fields in operations snapshots so the UI can show order links inside the Inbox. Keep retry keys idempotent for the same tenant, customer, conversation and payload. Demo source connections use stable conversation/message fixture IDs and retain local notes/replies across syncs. Live provider IDs, paging cursors and webhook deduplication belong to the backend.

The conversation toolbar also opens a local product quotation builder. Its catalog comes from `GET /operations`, including optional product `imageUrl`, `description`, `unit`, and `category`; see [product metadata and quotation rules](operations-api.md#product-catalog-and-local-quotations). A 1,000+ product catalog is searched/filtered and paged on the client, with up to 200 selected products per PDF. Downloading a quotation PDF does not call the message endpoint, attach or send a file automatically, create an order, or reserve stock. Sharing a downloaded PDF with a customer remains a separate, explicit action.

Demo data is stored under `smartsales.inbox.demo.v1`. The normal UI reset restores seed conversations while preserving canonical contacts and operations; new non-seed conversations are retained for reference compatibility. Explicit recovery after a corrupted Inbox load resets both Inbox and operations, with confirmation of the wider scope. This recovery spans two keys and is not atomic. Factory `reset()` is also used by isolated tests; application features must use `resetConversations()` for normal Inbox reset. Data and message changes survive browser reloads. Browser storage is not a secure location for real customer data. The demo contains synthetic Vietnamese customer profiles and fixed seed timestamps for 17 November 2026. AI suggestions in the UI are a local demonstration, not an external AI integration.
